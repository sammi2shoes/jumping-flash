# RS05 communication disconnect and recovery test

Prerequisite: the user physically passed standard RS05 watchdog A/B v4 after firmware0.5.0.14 update. Timeout0 remained RUN after1500ms; timeout20000 became disabled, with small position changes and confirmed final stops. This supports a functional timeout, not physical torque-removal latency.

This round uses two independent CAN nodes. Windows Python drives the official AT-format USB-CAN adapter (existing settings921600 serial /1Mbps CAN), host126/motor1. StickC Plus2 + MiniCAN observes the motor bus and remains connected when the USB-CAN branch is disconnected. The Stick uses normal CAN mode to provide ACKs, without ever sending an application frame. Listen-only would not acknowledge the motor when it is the only other node and could prevent reliable status reporting.

Upload firmware/WatchdogObserver/WatchdogObserver.ino with motor power removed. Open the Stick monitor at115200. Keep both adapters connected in parallel to the motor's existing CAN bus, preserving the user's proven wiring and termination; close MotorStudio and other adapter programs. The motor remains unloaded and secured with an accessible independent power cutoff. Button A does NOT stop the motor in this observer sketch.

Save scripts/watchdog_disconnect.py on the PC. pyserial is its only dependency (already used by the working GUI). Run `py watchdog_disconnect.py COM3`, substituting the actual USB-CAN adapter COM port, not the Stick port. Press Enter when physically ready to arm. It confirms stop, verifies standard timeout7028=20000, current7018=1 A, mode7005=2, and target700A=0. It enables RS05 type24 automatic reporting and requires repeated disabled feedback before enable. It verifies RUN/zero-speed configuration and reporting, then sends only zero-speed heartbeats. No nonzero target, save, fault clear, ID change, or calibration command is allowed.

When the PC prints HEARTBEAT ACTIVE, disconnect ONLY the USB-CAN adapter's CAN branch, keeping its USB connection, the Stick/MiniCAN/motor bus, and motor power intact. The PC stops and exits when motor feedback is absent for250ms and has no automatic reopen or enable path. Observe the Stick: fresh disabled feedback approximately1000ms after the last host command, with no explicit stop, no fault, and no dropped frames is consistent with the configured watchdog. If no disabled observation appears within2seconds, disconnect motor power rather than assuming safety.

After the script exits AND the Stick observes disabled, reconnect the USB-CAN branch while leaving the Python program closed. Watch at least5seconds of fresh disabled feedback (mode0, feedback_age low, flags0, invalid0). Unexpected RUN or enable after timeout is flagged. Stale feedback cannot establish recovery behavior. Paste both outputs. Timing measures received CAN command to received disabled report, with feedback/queue latency; it does not independently measure physical torque removal. Observer cannot detect the physical reconnection itself; the operator confirms that action.

Reboot the Stick observer before a separate repeat, because the recovery observation is deliberately latched. Ctrl+C on the PC requests a stop only while that adapter still has a working CAN connection. Motor power cutoff remains the stop when disconnected.

Validation: ESP32 compilation; C++ observer checks for measured interval, active reports addressed to motor, explicit stop exclusion, other-host and fault invalidation, unexpected enable/restart; Python simulated serial checks for framing with embedded delimiters, prerequisite readback/report gating, zero-speed whitelist, single enable, and no post-loss commands. No cloud hardware test was performed. On-device disconnect test pending.
